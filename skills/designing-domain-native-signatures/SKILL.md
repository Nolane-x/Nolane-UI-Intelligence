# Designing Domain-Native Signatures

## Parent Contract
**Required parent:** `deepening-signature-mechanisms`.

Receive experiential intent, user role/aspirational identity, product domain, task model, domain data/artifacts, selected visual ambition and anti-generic findings. The parent demands depth; this skill finds a signature whose causality comes from the subject itself.

## Subject-World Inventory
Build a **subject-world inventory** before styling: physical materials, instruments, recurring operations, spatial structures, quantities, transformations, notation systems, documents, signals, timelines, environmental cues, and expert gestures that actually belong to the domain. Separate real domain vocabulary from cinematic stereotypes about the domain.

## Mechanism Extraction
For promising subject artifacts ask: what property can become interface structure? A topology may become navigation only if relationships are real; a timeline may become choreography only if sequence matters; specimen morphology may influence shape only if it helps identity/comparison. Extract **domain-mechanism** before visual treatment.

Generate several signature candidates with different causal roots. At least one should be non-decorative: it should reveal, control, compare, navigate, explain or transform something real. Evaluate subject specificity, information gain, interaction depth, memorability, cost and accessibility.

## Signature Removal Test
Perform the **signature removal test**: remove the mechanism while preserving all content and utility. If the product feels almost equally specific, the “signature” is decoration. If removing it destroys task clarity, provide an accessible/reduced fallback rather than making the signature the only route.

## Trade-Dress Firewall
Use external references to learn mechanism classes, composition courage or rendering possibilities—not to clone recognizable arrangement, copy, palette, proprietary illustration, or branded motion. A **trade-dress firewall** records what was inspired, what was rebuilt from first principles, and which upstream surface cues were intentionally excluded.

## Cross-Context Survival
A valid signature must survive responsive recomposition, dense/empty/error states, localization, reduced motion and relevant accessibility modes. It can change form while preserving the same product-specific idea.

## Output — `domain-signature-brief`
Return `subject_world_inventory`, `candidate_mechanisms[]`, `selected_signature`, `domain_truth`, `information_or_interaction_role`, `removal_test`, `accessibility_equivalent`, `cross_viewport_strategy`, `trade_dress_firewall`, and `rendered_validation_plan`.

## Falsification
Replace the product name/content with a neighboring industry. If the same signature still looks equally plausible, it is a genre trope. Ask a domain expert what real concept the mechanism encodes; inability to answer falsifies domain-native status.

## Recovery
Return to the subject inventory, select a mechanism closer to real operations/data, simplify art direction, or make the signature deliberately quiet but structurally specific. Remove reference-derived visual cues that overpower domain truth.

## Hard gate
**A high-ambition signature cannot pass solely on novelty or beauty; it must bind to a real subject-world mechanism, survive the removal test and expected contexts, and document a trade-dress firewall for material external inspiration.**
