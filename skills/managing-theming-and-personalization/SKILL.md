# Managing Theming and Personalization

## Overview
Themes are semantic transformations, not palette inversion. Preserve role, hierarchy, contrast, focus, state, imagery, elevation, and accessibility while allowing brand and user preferences to vary what can safely vary.

## Parent Contract
**Required parent:** `routing-ui-work`.

Require token architecture, supported themes/brands, user-controlled dimensions, system settings, accessibility requirements, assets/illustrations, and persistence/sync behavior. Coordinate with token architecture rather than styling components independently.

## Decision Model
Separate invariant semantics from theme values. `surface-primary`, `text-muted`, `border-danger`, and `focus-ring` keep meaning while their concrete color/elevation values change. Do not expose primitive hex overrides as the main personalization API if they can destroy semantic contrast.

Define theme layers: system/default, brand, platform, mode, accessibility override, user preference, component context. Establish precedence and forbidden overrides. High-contrast/forced-color mode may bypass brand decoration to preserve operability. Dark mode changes luminance relationships, shadows/elevation, imagery, charts, syntax colors, and translucent materials — not just background/text inversion.

Personalization needs guardrails. Density, font scaling, accent, sidebar arrangement, or motion level can improve ownership, but settings that hide critical status, reduce target size below requirements, or remove focus cannot be allowed. Preview and restore defaults make experimentation safe.

Persistence should follow user expectations across device/account while respecting shared/public device privacy. When theme changes at runtime, avoid losing focus/scroll or flashing bright intermediate states.

## Evidence
Test every semantic state across themes, contrast/forced colors, system appearance switches, charts/illustrations/assets, disabled/focus/error/selected states, user font/density extremes, runtime transition, SSR/initial paint, and shared device. Automated contrast is necessary but not sufficient for hierarchy and imagery.

## Output Contract
Return a `theme-personalization-contract` with `semantic_invariants[]`, `theme_layers[]`, `precedence`, `token_mapping`, `dark_mode_rules`, `high_contrast_rules`, `personalizable_dimensions[]`, `forbidden_overrides[]`, `persistence`, `runtime_transition`, and `theme_tests[]`.

## Failure Traps
- Dark mode generated by invert filter or simple color swap.
- Brand accent used for semantic error/success in one theme.
- User personalization can hide focus or make tiny targets.
- High-contrast mode treated as another branded palette.
- Chart colors changed without preserving category distinction.
- Theme flash on load exposing sensitive or painful bright screen.
- Theme-specific component CSS diverging from shared semantics.

A theme is valid only if the product’s meaning survives the transformation.
