# Binding UI Evidence

## Overview
Evidence is useful only when a future reviewer can tell what was observed, how, against which artifact, and which claim it supports. This skill prevents “I checked it” from being treated as proof.

## Parent Contract
**Required parent:** `nolane-ui`.

Evidence may be generated by specialist skills, browser/runtime tools, deterministic validators, component explorers, accessibility tooling, visual comparison, or manual inspection. This skill owns binding and freshness, not the observation itself.

## Evidence record
For each observation record:
- `evidence_id`
- `method`
- `source`
- `artifact_or_revision`
- `scope`
- `claim`
- `observed_at`
- `result: PASS | FAIL | UNKNOWN`
- `artifact_digest` when available
- `environment` when behavior can vary by runtime/viewport/platform
- `notes`

## Evidence hierarchy
Prefer the closest observable oracle to the claim:
- geometry/fidelity → target and rendered screenshots plus measured layout when available
- interaction → executable interaction observation/test
- semantics → DOM/accessibility tree or platform semantic tree
- token consistency → deterministic token/component validation
- task flow → end-to-end task observation, not unit snapshots alone
- visual judgment → inspectable render and an independent critic, not source-code description

Do not use a weaker proxy when a direct oracle is available merely because the proxy is easier.

## Freshness
Evidence becomes stale when a later change can affect its claim. Compute staleness by overlap, not chronology alone. A copy edit need not invalidate a color-token check; a global type-token change invalidates typography and potentially layout/fidelity evidence across the product.

When in doubt, mark `UNKNOWN` and re-observe the smallest affected scope.

## Independence
For material aesthetic/UX completion, generator self-report may be logged as an observation but cannot be the only evidence closing the critic obligation. Deterministic tools may close deterministic claims; subjective claims require a critic or human review contract.

## Negative evidence
Preserve failures. A repair adds new evidence with a relationship such as `supersedes-after-repair`; it does not delete the original failure. This lets the release packet prove that the defect was actually encountered and re-tested.

## Screenshot evidence
A screenshot is not self-describing. Bind viewport, state, route/surface, theme, locale, interaction state, and target reference. A cropped screenshot cannot close a whole-screen obligation unless its scope says so.

## Automated audit evidence
Record tool identity/configuration and scope. “axe passed” or “Lighthouse 100” must not be expanded into “accessible” unless the obligation itself is explicitly limited to that automated check.

## Output: `evidence-ledger`
Return an append-only logical ledger of evidence records plus relationships: `supports`, `refutes`, `supersedes-after-repair`, `invalidated-by`, or `scoped-with`.

## Common failures
- Evidence with no artifact revision.
- Reusing a desktop screenshot to claim mobile behavior.
- Treating a static image as proof of keyboard behavior.
- Treating a source-code inspection as proof of rendered fidelity.
- Deleting or hiding failed observations after repair.
