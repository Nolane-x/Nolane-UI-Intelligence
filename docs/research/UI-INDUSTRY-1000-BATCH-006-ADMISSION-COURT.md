# UI Industry 1000 — Batch 006 Admission Court

This supplement records examples that were **rejected before canonical admission**. It exists to make the negative space of Batch 006 auditable: reaching 100 delivered skills did not authorize cosmetic decomposition.

## Governing rule

A candidate is rejected when deleting it and delegating its complete decision surface to an existing parent or sibling leaves no material decision or failure class unowned. Name novelty, platform labels, component labels, and repository popularity do not rescue an otherwise redundant candidate.

Canonical Batch 006 prose remains independently authored. This file is not a skill-prose template and does not authorize automatic generation.

## Explicit rejected shapes

- `governing-design-system-evolution` — rejected as a new root because existing design-system/component-system owners already govern the broad system; Batch 006 admits narrower compatibility, contribution, exception, migration and rollout authorities instead.
- `engineering-responsive-composition` — rejected as a competing responsive root; `adapting-responsive-layouts` remains authoritative and Batch 006 children own specific composition failures.
- `engineering-typographic-systems` — rejected as a competing typography root; `crafting-typography` remains the parent while runtime font/text specialists own distinct engineering failures.
- `designing-agentic-interaction-systems` — rejected as an umbrella duplicate of existing human-AI, autonomy, multi-agent and generative-UI owners.
- `engineering-ui-evidence-workflows` — rejected as an umbrella duplicate of evidence binding and existing verification authorities.
- `designing-responsive-dialog-to-sheet-transitions` — rejected because component-name × responsive-mode decomposition did not establish an independent failure topology.
- `designing-responsive-sidebar-to-drawer-transitions` — rejected for the same reason; navigation/component presentation mode is not automatically a canonical owner.
- platform-specific copies of token resolution, token inheritance or token typing — rejected as Cartesian platform × token expansion. Cross-platform differences belong in context/parity contracts unless a genuinely distinct decision appears.
- mobile/desktop/TV copies of typography fallback or loading rules — rejected when they merely rename the same font-runtime ownership by surface.
- component-specific copies of hover-to-touch adaptation — rejected; Batch 006 owns the modality transition across components rather than manufacturing a child for every widget.
- generic `designing-game-interfaces` — rejected because `designing-game-hud-and-menus` already owns the broad surface and Batch 006 only admits controller/focus/HUD/menu decisions that remain materially unowned.
- generic `designing-automotive-hmi` — rejected because `designing-automotive-interfaces` and `designing-high-stakes-decisions` already provide broad authority; Batch 006 admits specific vehicle-state and driver-safety decision owners.
- generic `designing-cross-device-experiences` — rejected as an umbrella. Session transfer, capability negotiation, state preservation, conflict resolution, companion authority and proximity cues have separable state/failure models and are routed independently.

## Boundary pairs reviewed explicitly

- token **version compatibility** vs **deprecation lifecycle** vs **adoption migration** vs **breaking-change rollout**: compatibility declares supported relationships; deprecation governs retirement state; migration governs consumer movement; rollout governs staged authority and blast radius.
- agent **approval scope** vs **scope drift**: the first establishes what was authorized; the second detects when evolving execution no longer fits that authorization.
- agent **retry/replay** vs **partial-completion recovery** vs **reversible actions**: retry/replay owns execution repetition semantics, partial recovery owns surviving work after interruption/failure, and reversibility owns undo/compensation after effects exist.
- **directional focus graphs** vs **rotary-controller focus navigation**: the first owns spatial focus topology for game/ten-foot surfaces; the second owns rotary stepping, acceleration, detents and automotive high-stakes focus behavior.
- **task-state preservation** vs **cross-device conflict resolution**: preservation reconstructs one continuation; conflict resolution converges two or more legitimate divergent revisions.
- **session handoff** vs **proximity handoff cues**: transfer mechanics do not own when nearby-device evidence is trustworthy enough to offer a transfer or how ambiguous presence is communicated.

## Admission conclusion

The delivered Batch 006 inventory remains exactly 100 because rejected shapes were replaced only by candidates with distinct decision ownership. No rejection was backfilled by noun substitution, brand naming, component multiplication, or platform multiplication.
