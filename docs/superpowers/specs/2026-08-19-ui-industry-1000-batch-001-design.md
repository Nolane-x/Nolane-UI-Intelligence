# UI Industry 1000 — Batch 001 Design

## Purpose

Batch 001 begins the expansion of Nolane UI Intelligence from 174 broad canonical faculties toward an eventual 1,000-skill UI-industry coverage graph. The target is not a numerical prompt collection. Every promoted skill must own a decision, behavior, failure topology, or verification problem that cannot be delegated cleanly to an existing owner without losing important conditional reasoning.

The first batch adds exactly 100 specialist faculties. They are deliberately concentrated in under-decomposed areas of the current graph: motion semantics, rich controls, direct manipulation, data/spreadsheet interaction, enterprise workflow, billing/scheduling/geospatial interaction, and history/conflict surfaces.

## Non-negotiable authorship constraints

1. No loop-generated skill prose.
2. No Cartesian-product generation such as domain × component × platform.
3. No numbered or cosmetically renamed variants.
4. No bulk copying of third-party skill text.
5. Third-party sources may be adopted only when their license, provenance, scope and adaptation boundary are explicit; otherwise NUI synthesizes mechanisms in original prose.
6. Repository automation may validate, index, deduplicate, route, count and test. It may not author the substantive skill bodies.
7. Shared headings are permitted where they serve NUI contracts, but the reasoning content, decision model, failure topology, evidence and verification obligations of every skill must be independently authored.
8. A specialist child may narrow or strengthen its parent; it may not waive the parent’s accessibility, product-truth, evidence, platform or completion obligations.

## Promotion gate

A candidate is promoted only when all of the following are defensible:

- **Distinct trigger:** there is a recognizable task or failure that should activate the skill.
- **Distinct decision ownership:** the skill makes at least one material decision not already completely owned by another faculty.
- **Boundary:** it names what remains owned by parent/sibling faculties.
- **Conditional model:** it contains trade-offs, not a single preferred recipe.
- **Failure topology:** it explains characteristic ways the interface fails.
- **Accessibility/platform consequences:** relevant non-visual behavior is explicit.
- **Falsification:** there is a way to prove the skill’s output inadequate.
- **Recovery:** it can react when assumptions fail.
- **Output contract:** downstream work can consume a bounded artifact or decision record.

A candidate that is only a visual treatment becomes a pattern/reference, not a canonical skill. A candidate already covered by an existing owner is merged or rejected.

## Parent strategy

Batch 001 does not invent new broad orchestrators merely to hold new children. It deepens existing owners:

- motion specialists → `designing-motion`
- rich controls → `engineering-rich-interactive-components` or `designing-interactions`
- manipulation specialists → `designing-pointer-touch-pen-input` / `engineering-rich-interactive-components`
- spreadsheet/data specialists → `designing-data-dense-interfaces` / `designing-data-visualization`
- enterprise workflow specialists → `designing-task-flows`, `designing-collaboration-and-presence`, or `routing-ui-work` where no narrower parent is semantically correct
- transaction specialists → `designing-financial-transaction-ui` / `designing-commerce-checkout`
- temporal/scheduling specialists → `designing-task-flows` / `designing-real-time-updates`
- geospatial specialists → `designing-data-dense-interfaces` or `designing-pointer-touch-pen-input`
- history/conflict specialists → `designing-collaboration-and-presence` / `designing-interactions`

## Source policy for this batch

Primary and mature sources are mechanism evidence, not text reservoirs. The batch uses the repository’s existing authority hierarchy and source ledger. In particular:

- WAI-ARIA Authoring Practices Guide for custom widget semantics and keyboard/focus models such as combobox, menu, dialog, grid, tree, treegrid, tooltip and window splitter.
- Apple Human Interface Guidelines for platform expectations around menus, drag/drop, motion, direct manipulation and system surfaces.
- WCAG 2.2 and existing NUI accessibility faculties for keyboard, focus, alternatives, target size, motion safety and robust semantics.
- Carbon, Fluent, Material and Spectrum as mature design-system corroboration when component anatomy or state coverage differs by ecosystem.
- OpenDesign, VoltAgent/awesome-design-md, bergside/awesome-design-skills and other community corpora only as discovery/mechanism sources. NUI does not bulk-copy their prose or treat brand styling as authority.

## Quality shape of individual skills

The skill corpus is intentionally heterogeneous, but every file must contain enough information to answer these questions without reading its implementation history:

- What task triggers this faculty?
- What exact decision does it own?
- Which parent obligations remain in force?
- What state/action model matters?
- What are the dangerous or ambiguous edge cases?
- What input modalities/accessibility concerns materially alter the design?
- What evidence is appropriate?
- How can the recommendation be falsified?
- How does the skill recover when its assumptions fail?
- What does it return downstream?

## Graph and routing requirements

Every new directory under `skills/` must have a matching graph entry. No new root is introduced. Parent chains must terminate at the existing root. Output identifiers must be semantically specific enough that downstream consumers can distinguish sibling outputs. The router must continue to load the smallest sufficient faculty set; the existence of 274 skills after this batch is not permission to preload all of them.

## Documentation and evidence requirements

Batch 001 adds a coverage inventory and a provenance note explaining that the new skills are original NUI synthesis. Source links may be shared across multiple skills when the authority covers the same semantic primitive, but each skill must state the mechanism it learned rather than claiming the source authored the NUI skill.

## Verification gates

Before integration:

1. All 100 directories and `SKILL.md` files exist.
2. Frontmatter `name` equals directory slug.
3. Every new skill has a graph entry with a valid existing/new parent.
4. Graph remains acyclic and all nodes reach `using-nolane-ui`.
5. No duplicate slug exists.
6. A lexical/semantic overlap review records any close sibling and explains the boundary.
7. Repository validators and unit tests pass.
8. Documentation skill count is updated only after the graph and filesystem agree.
9. Final completion claim is bounded to structural and authored-corpus evidence; it does not claim empirical superiority of NUI.

## Batch completion definition

Batch 001 is complete when the branch contains 100 independently authored specialist skills, the graph and docs describe 274 canonical skills, validation passes, and no known ownership collision remains unresolved. The eventual 1,000 target remains a roadmap objective, not a claim that this single batch covers the entire industry.
