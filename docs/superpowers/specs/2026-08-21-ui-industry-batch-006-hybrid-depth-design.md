# UI Industry Batch 006 — Hybrid Depth Expansion Design

Date: 2026-08-21  
Status: design contract awaiting review  
Baseline: `main@3fece1b74051b53830e0f677503533cf44d633d1`  
Canonical baseline: 774 skills  
Target after implementation: 874 canonical skills

## 1. Objective

Batch 006 adds exactly 100 canonical UI faculties only after each candidate demonstrates decision ownership that is absent from the 774-skill baseline. The batch intentionally combines deeper decomposition of broad NUI roots with interaction surfaces whose runtime failure models are materially different from conventional web/mobile CRUD.

The delivery target is numerical only after semantic admission. A weak candidate is rejected and replaced from the research pool; it is never padded into the graph merely to reach 100.

## 2. Non-goals and hard prohibitions

Batch 006 does not create a larger prompt, a library of aesthetic adjectives, a catalog of branded products, or mechanically differentiated variants of the same reasoning unit.

The following are prohibited:

- loops, templates, or generators that write or rewrite `SKILL.md` prose;
- noun substitution over a shared body;
- Cartesian expansion such as domain × component, platform × token, breakpoint × widget, or device × workflow;
- one skill per brand, repository, library, component name, chart type, or visual style;
- reusing prose from closed PR #19 or any abandoned batch;
- treating minimum character count as evidence of semantic depth;
- admitting a candidate because its name sounds narrower than an existing owner;
- copying trade dress, product identity, or recognizable visual expression from external references;
- allowing a generating agent to self-certify its own semantic uniqueness or release readiness.

Automation is permitted for deterministic repository mechanics: counting, graph serialization, hashes, schema validation, parent-chain checks, normalized duplicate detection, similarity alarms, test execution, provenance bookkeeping, and exact-revision verification. It may not author skill reasoning.

## 3. Admission law

A candidate may enter the canonical graph only when all of the following are true:

1. **Unique trigger** — there is a concrete situation in which routing to the candidate is justified.
2. **Material decision owner** — the candidate owns a decision that cannot be delegated losslessly to its parent or sibling.
3. **State/invariant model** — the skill has state, constraints, or invariants specific enough to reason about failure.
4. **Characteristic failure topology** — the failure is not merely generic poor usability, inconsistency, or inaccessibility.
5. **Runtime falsifier** — a reviewer can construct an observation or experiment capable of disproving the skill's claimed adequacy.
6. **Recovery strategy** — the skill can prescribe recovery when its invariant is violated.
7. **Bounded output** — the output contract is narrower than a generic design recommendation.
8. **Sibling exclusion boundary** — the spec says what adjacent owners retain.
9. **Current evidence** — the mechanism is grounded in current authoritative material or stable platform behavior.
10. **Delete-the-skill test** — removing the skill and assigning its scope to the parent/sibling must cause at least one material decision or failure class to lose an owner.

If criterion 10 fails, the candidate is rejected even if the prose could be made long or sophisticated.

## 4. Authority model

The inventory below names an authority family rather than inventing bridge nodes. During implementation, every candidate must attach to the existing canonical owner that actually holds that family at the 774-skill baseline. If no legitimate parent exists, the candidate is rejected or the graph architecture is separately reviewed; implementation must not manufacture a meaningless parent merely to satisfy topology.

Known broad roots include `architecting-design-tokens`, `architecting-component-systems`, `adapting-responsive-layouts`, `crafting-typography`, `designing-human-ai-interaction`, `designing-agent-autonomy-and-control`, `designing-ai-uncertainty-and-provenance`, `designing-multi-agent-surfaces`, and `designing-generative-ui`. Batch 006 decomposes them only where a distinct failure class exists; it does not restate them.

## 6. Explicitly rejected candidates

The candidate pool is intentionally larger than the admitted set. Rejections are evidence that the quota is not driving ontology.

- `designing-dialog-to-sheet-transitions` — rejected because it risks responsive × component expansion; the generic modality/composition owner can reason about it.
- `designing-sidebar-to-drawer-transitions` — rejected for the same reason.
- `designing-optical-size-typography` — rejected because existing `crafting-typography` already owns optical sizing as part of its core type system reasoning.
- `designing-multiscript-font-fallback` — rejected because globalization/script/fallback faculties already exist and a second owner would blur authority.
- platform-specific token copies such as “mobile tokens”, “TV tokens”, or “automotive tokens” — rejected as Cartesian duplication.
- generic `designing-gamepad-focus-navigation` — rejected in favor of separating actual spatial focus topology from remote-control semantics and controller ownership.
- repository-named faculties — rejected; a source repository can support many mechanisms but is never itself an ontology node.

Any admitted candidate may still be removed during implementation if full baseline inspection reveals an existing semantic owner missed by filename-level review.

## 8. Individually authored skill contract

Each of the 100 `SKILL.md` files must be written independently from the candidate's decision model. Common section labels are allowed where they help routing, but identical paragraph skeletons with substituted nouns are not.

Every new canonical skill must contain, in its own words and appropriate structure:

- parent/authority contract and explicit exclusions;
- trigger and routing boundary;
- decision/state model with invariants;
- characteristic failures and why adjacent owners cannot resolve them alone;
- evidence obligations appropriate to the mechanism;
- falsification procedure using observable runtime/artifact evidence;
- recovery or repair behavior;
- bounded output contract and handoffs.

Not every skill needs the same number of sections, examples, tables, or prose length. Semantic specificity outranks uniform formatting.

## 9. Graph and routing integration

Implementation must add only admitted skills to `skills/skill-graph.json` and preserve the smallest-sufficient-routing principle. Parent links must resolve to existing canonical owners. No bridge node is created solely to make the batch look taxonomically neat.

Routing tests must prove at least:

- each new specialist can be reached by its own trigger class;
- broad parent prompts do not automatically route to all descendants;
- sibling-specific prompts prefer the correct owner;
- cross-court prompts can compose owners without duplicating authority;
- existing baseline routes remain valid unless an intentional decomposition is documented.

## 10. TDD and semantic quality gates

Before canonical prose is implemented, Batch 006 must introduce failing acceptance tests for the batch contract. The implementation then proceeds until those tests and the pre-existing suite pass.

The batch-specific gates are:

1. exactly 100 admitted Batch 006 slugs and 874 canonical skills at completion;
2. all slugs unique and all files mapped exactly once into the canonical graph;
3. all parent chains resolve;
4. required admission evidence is present in the Batch 006 inventory/provenance record;
5. no normalized exact duplicate body;
6. alarms for suspicious near-rename similarity, repeated long shingles, mass paragraph reuse, and unusually identical section skeletons;
7. explicit sibling-boundary and delete-the-skill rationale for every new owner;
8. no repository script or generator writes or rewrites `SKILL.md` prose;
9. README/current-count surfaces synchronized only after exact graph verification;
10. full existing unit test suite remains green;
11. `python scripts/nui-validate .` passes on the exact candidate revision;
12. completion evidence records the exact commit SHA being claimed;
13. CI on the exact head must be green before merge.

Similarity alarms do not autonomously reject a skill. They route suspicious pairs to semantic review, because independently valid skills may share required vocabulary. Conversely, low lexical similarity does not prove unique ownership.

## 11. Implementation slicing

The 100-skill batch may be committed in technical slices to reduce review risk, but technical slices must not become quota generators. A recommended sequence is:

1. add batch acceptance tests and provenance/inventory scaffolding;
2. author Court A and integrate/test its graph edges;
3. author Courts B and C and verify overlap with existing responsive/globalization/typography owners;
4. author Court D and verify overlap with all existing AI/autonomy/provenance/generative-UI owners;
5. author Court E and verify separation between evidence construction, critique, and release authority;
6. author Courts F and G with platform-behavior evidence and modality-specific falsifiers;
7. author Court H and verify separation from responsive state, collaboration conflict, sync, and notification navigation;
8. run global duplicate/graph/routing/provenance review;
9. synchronize counts and release evidence only after the graph is exactly 874;
10. run exact-head repository verification and CI.

A court can lose a candidate during authoring. When this occurs, implementation returns to the research pool and admits a genuinely different candidate through the same law; it does not clone a sibling to preserve the budget.

## 12. Failure and recovery policy

If the current `main` branch changes materially before implementation, Batch 006 must re-audit semantic overlap against the new baseline before graph insertion. A clean merge base is not proof that decision ownership is still unique.

If a candidate is discovered to overlap after prose has been authored, the default action is deletion or consolidation, not argumentative preservation of sunk work.
