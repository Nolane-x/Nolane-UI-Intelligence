# Usage

## Start a material UI task

Load `using-nolane-ui`. The bootstrap hands lifecycle ownership to `nolane-ui`, which compiles a contract, routes faculties, and creates release obligations before the task can make a material completion claim.

Do **not** preload all 47 skills. Progressive disclosure is a design constraint.

## Example: expert AI-agent operations dashboard

A likely route is:

`using-nolane-ui → nolane-ui → ui-contracting → routing-ui-work`

Then selected faculties can include:

`modeling-product-intent`, `modeling-users-and-tasks`, `architecting-information`, `designing-navigation`, `designing-interactions`, `modeling-component-states`, `designing-data-dense-interfaces`, `exploring-aesthetic-directions`, `directing-visual-hierarchy`, `architecting-design-tokens`, `architecting-component-systems`, `adapting-responsive-layouts`, `designing-accessible-interfaces`, and the relevant critics.

A marketing landing page would route differently; a faithful screenshot reproduction would emphasize fidelity; a small form fix may use a reduced path.

## What an agent should produce before code

For material new design, the exact artifacts depend on routing, but the design must be specified enough that implementation does not invent material product/visual decisions. Typical artifacts include:

- UI contract with authority/fidelity/non-goals
- task profile and selected faculties
- product/user/task model
- IA/task-flow/interaction contracts as needed
- aesthetic direction with rationale
- hierarchy/composition/type/color/spacing contracts
- design-token/component-state contract
- responsive/accessibility obligations

If a trusted design source already fixes some axes, record those as frozen and skip redundant divergence rather than redesigning for ceremony.

## During implementation

Treat the selected design/system contracts as production constraints. If code reveals an unresolved material decision, return to the earliest relevant design phase instead of making a one-off choice and hiding it in CSS.

Use existing project components when their semantics match. A component's existence is not proof it is the correct pattern.

## Verification

After an inspectable render exists:

1. Run `challenging-ui-designs` with the task's verification lenses.
2. Bind browser/screenshot/test/accessibility/token evidence through `binding-ui-evidence`.
3. Repair findings through `recovering-ui-work` when needed.
4. Re-test affected/transitive obligations.
5. Submit a bounded packet to `gating-ui-completion`.

Strict fidelity work requires an authoritative target and inspectable render. Static source code cannot close a visual-fidelity obligation.

## Reduced path for small changes

A small local change can skip discovery/divergence/systemization only when:

- product semantics/IA/visual direction are already established,
- the change does not introduce a new interaction/component family,
- omitted faculties have no material failure mode for the change, and
- relevant regression/accessibility/state verification still occurs.

Record this decision; do not use “small change” as a universal bypass.

## Applying NUI as an audit-only system

For audit requests, preserve the existing artifact. Route critic faculties directly after contract/profile creation. Critics use `may_modify: false`; they report findings. If the user then asks to repair, create a repair scope and use recovery/implementation rather than letting the critic silently rewrite its evidence target.

## Completion language

Use bounded claims:

> The current desktop render was compared with the accepted target for the reviewed routes/states; the primary keyboard flow and declared automated accessibility checks passed. Native-mobile screen-reader behavior and untranslated locales were not tested.

Avoid absolute labels such as “pixel-perfect,” “fully accessible,” or “production-ready” unless the packet actually contains evidence for that exact scope.
